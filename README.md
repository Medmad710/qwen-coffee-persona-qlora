# Применение QLoRA для настройки тональности модели Qwen2.5-7B-Instruct

Репозиторий содержит пайплайн синтеза данных, автоматического разделения выборки, эффективного дообучения (Fine-Tuning) и автоматизированной оценки модели для создания специализированного ассистента со стилистикой 'дружелюбного бариста"

Тема датасета и проекта была обусловлена спецификой компаний Steppe coffee/Circle

## Обоснование выбора модели
Среди современных LLM малого масштаба отсутствует абсолютный (State-of-the-Art) SOTA-лидер для мультиязычных задач. Выбор архитектуры Qwen2.5-7B-Instruct обусловлен следующими факторами:
1. Высокая базовая точность при работе с языками, отличными от английского
2. Оптимальный размер параметров , позволяющий проводить эффективное дообучение методами снижения ранга на доступных ресурсах google colab T4 GPU.
3. Развитая экосистема ,наличие документации и воспроизводимых гайдов для интеграции в production-пайплайны.

## Конфигурация обучения
Параметры fine-tuning зафиксированы в `src/config.yaml`. Обучение проводилось в режиме 4-bit квантования на графическом процессоре T4 GPU.
Основные параметры:
- model_name: "Qwen/Qwen2.5-7B-Instruct"
- per_device_train_batch_size: 2
- gradient_accumulation_steps: 4
- learning_rate: 2e-4
- num_train_epochs: 3
- max_length: 512
- bf16: true
- gradient_checkpointing: true
- 
## Методология сборки датасета (Синтез через LLM)
Так как готовых открытых датасетов со спецификой локального кофейного рынка и уникальной тональностью не существовало, было принято решение полностью синтезировать обучающую выборку с использованием генеративных моделей.

Процесс состоял из следующих этапов:
1. **Генерация сырых данных**: С помощью API-интерфейсов старших языковых моделей был сгенерирован массив пар формат `instruction-response` (всего 205 уникальных примеров). Ноутбук прототипирования находится в `notebooks/data_synthesis.ipynb`
2. **Фильтрация и очистка**: На этапе постобработки был написан скрипт очистки дубликатов, удаления пустых ответов и базовой фильтрации качества, исключение обрывков текста и галлюцинаций Результат сохранен в формате JSONL (`data/coffee_dataset.jsonl`)
3. **Разделение выборки**: Скрипт `data/split_dataset.py` автоматически разбил очищенный массив на обучающую выборку 184 примера, `train.jsonl` и отложенный тестовый датасет для валидации 21 пример, `test.jsonl`.

## Пайплайн и конфигурация Fine-Tuning
Дообучение модели представляет собой полный воспроизводимый пайплайн. 

Все изменяемые параметры вынесены из исполняемого кода скриптов в глобальный конфигурационный файл `configs/lora_config.yaml`. 

Процесс fine-tuning реализован в скрипте `src/fine_tune.py` через интеграцию библиотек Hugging Face PEFT и Transformers:
1. **Загрузка базовой архитектуры**: Модель `Qwen/Qwen2.5-7B-Instruct` инициализируется в режиме 4-bit квантования с помощью `BitsAndBytesConfig` для снижения требований к видеопамяти.
2. **Конфигурация LoRA**: Обучаются только добавленные веса исходные соответствено заморожены
3. **Параметры итерации**:
   - learning_rate: 2e-4
   - num_train_epochs: 3
   - per_device_train_batch_size: 2
   - gradient_accumulation_steps: 4
   - max_length: 512
   - bf16: true
   - gradient_checkpointing: true

Потери при обучении train/loss стабильно снизились с начального значения 2.2 до значения 0.5 на финальных шагах. 
Валидационные потери eval/loss снизились с 1.12 до стабильного плато в районе 1.04: что указывает на успешную сходимость без переобучения. 
(Все логи шагов автоматически экспортировались в Weights & Biases)

В конце работы скрипт сохраняет не всю массивную модель, а исключительно легковесные веса адаптера в папку `models/coffee_qwen_adapter/`.

## Результаты оценки (Evaluation)

### 1. Автоматические метрики (ROUGE, BERTScore)
Расчет ROUGE и семантического соответствия векторов - BERTScore на тестовой выборке показал следующие результаты:

```json
{ 
  "rouge/base_rougeL_mean": 0.0238, 
  "rouge/tuned_rougeL_mean": 0.0476,
  "bertscore/base_f1_mean": 0.6482, 
  "bertscore/tuned_f1_mean": 0.7147
}

```

Анализ автоматических метрик

* Метрики семейства ROUGE демонстрируют крайне низкие значения для обеих моделей. Это обусловлено спецификой задачи Style Transfer: "генерация естественного диалога предполагает высокую вариативность синонимов и речевых оборотов, что делает посимвольное совпадение n-грамм с эталоном неэффективным критерием оценки"
* BERTScore подходит лучше и зафиксировал прирост среднего значения F1 с 0.64 до 0.71, что подтверждает сдвиг семантического вектора дообученной модели в сторону целевого контекста.

### 2. Методология LLM-as-a-judge

В качестве независимого эксперта-судьи была использована модель gemini-3.1-flash-lite, оценивающая соответствие заданной роли и сохранение фактологии.

Итоговая статистика сравнения:

* Победила базовая модель (Model_A): 2
* Победила дообученная модель (Model_B): 17
* Ничья (Tie): 2

## Технические нюансы и проблемы в процессе реализации
В ходе прохождения полного цикла — от подготовки данных до деплоя и оценки — был зафиксирован ряд инженерных нюансов, потребовавших оптимизации:

1. **Ограничения аппаратных ресурсов VRAM**: При стандартном обучении 7B модели на бесплатном GPU уровня T4 в Google Colab неизбежно возникала ошибка `Out Of Memory `. Проблема была решена жестким ограничением максимального контекста токенизатора `max_length: 512`, включением `gradient_checkpointing` для разгрузки памяти при бэкпропе и накоплением градиентов `gradient_accumulation_steps: 4` при физическом размере батча 2
2. **Стабильность обучения (Выбор типа данных)**: Использование стандартного `fp16` приводило к локальным всплескам градиентов и нестабильному лоссу из-за особенностей квантованных весов Qwen2.5. Переход на тип данных `bf16: true` полностью исправил сходимость)
3. **Ограничения классических метрик валидации**: На этапе оценки выяснилось, что стандартная метрика n-граммного сходства `ROUGE` выдает околонулевые значения 0.02 и 0.04 как для базовой, так и для дообученной модели. Это доказало неприменимость ROUGE для задач Style Transfer, где один и тот же смысл может быть выражен абсолютно разными словами и оборотоми, что привело к необходимости внедрения архитектуры `LLM-as-a-judge` на базе Gemini API для прагматического анализа ответов , была выбрана gemini-3.1-flash-lite по причине увеличеного плана на RPD - Peak requests per day в 500 ед.


### Выводы

* Необходимость LLM-as-a-judge: Результаты эксперимента подтверждают, что для задач изменения тональности и стиля автоматические метрики (ROUGE) малоинформативны. Использование более мощной языковой модели в роли судьи позволяет оценивать прагматику текста, контекстуальную уместность и следование роли, что дает релевантную оценку качества
* Соответствие стилю: Базовая модель Qwen2.5 генерировала избыточно формальные, структурированные ответы (нумерованные списки с сухими фактами при запросе кофеина, лекции о факторах экстракции). Обученный LoRA-адаптер успешно перестроил тональность: модель нативно использует разговорные формулировки, профессиональный сленг («хоппер», «натуральная обработка», «воронка V60») и предлагает комплименты для сглаживания негативного опыта клиентов


* Важно заметить: Локальное квантование и наложение адаптеров низкого ранга не вызвали деградации общих знаний базовой модели. Специфика рецептур заваривания и дескрипторов сортов кофе обрабатывается корректно.
